# 06 · ADR-0001 — 언어·UI 스택 선정

> 상태: **📐 제안 — 사용자 판단 대기.** 채택 시 [docs/10](10-decision-record.md)에 DR로 승격.
> 판정 기준 = [00 §3](00-vision.md) 예산(유휴 RSS ≤5MB·exe ≤3MB·외부 DLL 0) + 개발 효율 + 기존 자산 재사용.

## 1. 문제

트레이 상주 + 소형 창 2개(Top 5 팝업·프로세스 트리 뷰) + Win32/NT 시스템 콜 다수를 구현할 스택.
**도구 자신의 상주 점유가 곧 제품 품질**이므로, 런타임이 무거운 스택은 목적과 정면 충돌한다.

## 2. 후보 비교

| | A. **Rust + windows-rs (Win32 직접)** | B. C/C++ + Win32 | C. C# .NET (WinForms) | C′. C# NativeAOT | D. Go + 트레이 라이브러리 |
| --- | --- | --- | --- | --- | --- |
| 예상 exe | 1~3MB | **0.1~0.5MB** | 1MB+런타임(또는 self-contained 60MB+) | 4~10MB | 6~12MB |
| 예상 유휴 RSS | **3~5MB** | **2~4MB** | 30~80MB ❌ | 15~25MB ❌ | 10~20MB ❌ |
| 외부 의존 | 0 (OS 인박스만) | 0 | .NET 런타임 | 0 | 0 |
| Win32/NT 콜 접근 | windows-rs 전체 커버(Nt* 포함 수동 선언 용이) | 네이티브 그 자체 | P/Invoke 다량 필요 | P/Invoke 다량 | syscall/cgo 마찰 큼 |
| 메모리 안전 | ✅ 컴파일 타임 | ❌ 수동 | ✅ GC | ✅ GC | ✅ GC |

## 3. 판정 (기준: **DR-4 — 성능·동작 안정성 > 개발·배포 편의성**, 08-07 추가)

- **C·C′·D 탈락**: 유휴 RSS가 예산(≤5MB)의 3~15배 + GC 정지·점유 변동(안정성 열세). "메모리 아끼는 도구가 메모리를 낭비"하는 자기모순 — 협상 불가. 이들의 유일한 우위(개발 속도)는 DR-4 기준상 판정 근거가 아니다.
- **B(C/C++) vs A**: 성능은 사실상 동급(둘 다 네이티브·GC 없음, 차이는 예산 내 ~1-2MB). 갈리는 축은 **동작 안정성** — 상시 상주 + 타 프로세스 핸들·미문서 NT API를 다루는 프로그램에서 수동 메모리 관리(B)는 크래시·누수 면적을 키우고, 컴파일 타임 안전(A)이 구조적 우위. DR-4 기준으로도 A가 B를 이긴다(편의성 논거 불요).
- **A(Rust) — 권고안**: 예산 충족 + 안전성 + `nexa-dir2`에서 **동일 요구(단일 exe·초저메모리·Win32 직접·커스텀 드로잉)를 이미 실증**(exe 3.43MB·유휴 RSS 16.86MB — 본 프로젝트는 탐색기보다 훨씬 작아 5MB 목표 현실적). 컨트롤 라이브러리(ctl)·CI·패키징 재사용은 부수 이득.

**권고: A — Rust + windows-rs, Win32 직접 호출, nexa-dir2 자산 이식.**

## 4. 권고안 세부 (채택 시 초기 구조)

- 크레이트: `mk-core`(관찰·정리 엔진 — 순수 로직, 단위 테스트 대상) + `mk-app`(bin — 트레이·창·메시지 루프). 전부 rlib 정적 링크 = 단일 exe.
- UI: 창 1개당 Win32 등록 클래스 + 커스텀 드로잉(nexa-dir2 ctl 차용 — label/button/checkbox/spin/searchbox면 설정 창 충분).
- 스레딩: UI 스레드 1 + 관찰 타이머(트레이 스레드 겸용) + 정리 실행은 짧은 워커. 통지 PostMessage(nexa-dir2 A-1 세대 가드 계승).
- 릴리스 프로파일: `opt-level="z"`·LTO·strip — nexa-dir2 설정 재사용.

## 5. 되돌림 조건

M0(트레이+관찰 수직 슬라이스) 실측에서 유휴 RSS > 5MB 또는 exe > 3MB가 나오고 원인이 스택 고유 비용이면 B(C) 재검토. GUI 생산성이 병목이면 범위 축소가 우선(스택 변경은 최후).

## 6. 재검토(08-07, 사용자 요청) — "시스템 콜이 많은데 C++ 대신 Rust로 괜찮은가"

시스템 콜 비중이 높은 프로그램 특성을 전제로 Rust vs C++를 축별 심층 비교. **결론: DR-5(Rust) 유지.**

### 6-1. 시스템 콜 호출 비용 — 차이 없음 (기계어 수준 동일)

- windows-rs는 **런타임·마샬링 계층이 없는 선언 전용 바인딩**이다. Rust의 `extern "system"` 호출은 C++와 똑같이 **IAT 간접 call 1개**로 컴파일된다 → `ntdll`/`kernel32` 스텁 → `syscall` 명령. 호출 경로가 바이트 단위로 동일하다(C#의 P/Invoke 마샬링·GC 핀 비용 같은 것이 존재하지 않음).
- 콜 1회 비용은 **유저→커널 전환(~1μs급)과 커널 측 작업이 지배** — 언어가 개입할 자리가 없다. `NtQuerySystemInformation`으로 300개 프로세스를 읽는 시간의 99%는 커널이 쓴다.
- 결과 버퍼 파싱(가변 길이 구조체 워킹): 둘 다 포인터 산술 수준 코드로 최적화된다. Rust의 경계 검사는 slice 순회에서 대부분 컴파일러가 제거하고, 잔여분도 분기 예측 적중으로 측정 한계 이하.

### 6-2. 상주 메모리 — C++가 <1MB 우위 (예산 내 무의미)

| | C++ (MSVC, 최소 CRT) | Rust (std, panic=abort) |
| --- | --- | --- |
| 유휴 RSS 기대치 | ~1.5–3MB | ~2–4MB |
| 힙 | CRT heap → `HeapAlloc` | 기본 할당자 = **동일한 Windows Heap**(`HeapAlloc`) |
| exe (이 규모, strip+LTO) | ~0.1–0.5MB | ~0.5–1.5MB |

차이의 원천은 Rust std의 포맷팅·패닉 기반 코드 수백 KB뿐이다. 힙 동작(커밋·디커밋·워킹셋)은 같은 OS 힙이라 **회수 특성도 동일**. 예산(RSS ≤5MB·exe ≤3MB) 안에서 두 언어 모두 여유 — 실측 근거: Mem Reduct(C) ~2–4MB vs `nexa-dir2`(Rust, 훨씬 큰 앱) 16.86MB → 이 규모 Rust 앱은 3–5MB권.

### 6-3. 반응 속도 — 차이 없음

- 둘 다 GC·JIT·인터프리터 없음 → **정지 시간 0, 지연 분산 없음**(상주 도구에 중요). 트레이 팝업 <100ms·트리 뷰 <300ms 예산은 시스템 콜+GDI 시간이 지배하며 언어 무관.
- 코드젠은 양쪽 다 성숙한 최적화 백엔드(인라인·벡터화 동급). `panic=abort`로 언와인드 오버헤드도 제거.

### 6-4. 갈리는 축 = 동작 안정성 (DR-4 최상위 기준)

이 프로그램의 위험 지점은 정확히 C++의 약점과 겹친다:
- **가변 길이 커널 버퍼 워킹**(`SYSTEM_PROCESS_INFORMATION` NextEntryOffset 체인) — C++ 오버런·오프바이원의 전통적 온상. Rust는 경계·수명 검사로 차단.
- **24/7 상주** — 미세 누수·UAF·이중 해제가 시간과 함께 누적 → Rust는 소유권으로 컴파일 타임 차단(NFR-3 게이트와 상승 작용).
- **스레드 경합**(UI + 타이머 + 워커 통지) — Rust는 `Send`/`Sync`로 데이터 레이스를 타입 수준 차단.
- Rust에서도 FFI 경계는 `unsafe`지만, [15 §4](15-dev-methodology.md) 규율로 좁게 격리·주석 강제 — C++는 프로그램 전체가 그 상태다.

### 6-5. 종합

성능·반응 축 **동률**(기계어 동일), 메모리 축 C++ 우위 **<1MB**(예산 대비 무의미), 안정성 축 **Rust 우위**(위험 지점과 정합). DR-4 기준(성능·안정성 > 편의성)으로 재판정해도 결론 불변 — **Rust 유지**. 단 §5 되돌림 조건은 그대로 살아 있으며, M0 실측이 최종 심판이다.
