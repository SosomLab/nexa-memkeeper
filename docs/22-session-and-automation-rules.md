# Ⅰ부. 세션 분담

전역 규칙의 틀(개발 = Fable · 협업 = Opus · 파일 단위 세마포어)을 그대로 쓰고, 아래만 이 저장소에 맞춘다.

## 1. 누가 무엇을 하나

| 일 | 세션 |
| --- | --- |
| 설계 결정(ADR · DR · [09](09-settings-schema.md) 설정 스키마의 **내용**) · 새 기능 · 결함·성능 **원인 분석** · 릴리스(버전 · 태그) | 개발 |
| 회수 엔진 · NT/Win32 API 호출 · `unsafe` · 메시지 루프 · 셸↔워커 인자 규약 · 설정 파일 포맷 · 예산 게이트(DR-8)에 영향을 주는 변경 | 개발 |
| `mk-core`와 `mk-app` 양쪽, 또는 소스 · 패키징 · CI 중 두 영역 이상에 걸친 변경, 또는 약 200줄 이상 | 개발 |
| 패키지 설치·제거 방식, CI 게시 흐름의 변경 | 개발 |
| 상태 점검(CI · git · choco 패키지 페이지 · winget PR 라벨 · 이 PC의 프로세스·레지스트리 **읽기**) · 조사·탐색 보고 | 협업 |
| fmt · clippy · test · 릴리스 빌드 · 재기동 · 예산 실측 · 스모크 · `scripts/measure/` 실측의 **실행** | 협업 |
| 기록(journal · DEVLOG · STATUS · TODO · MILESTONES · BRANCHES · README · Wiki · 릴리스 노트) | 협업 |
| 간단 수정(오타 · 문구 · i18n 문자열 · 주석 · 설정 기본값 · 린트/포맷 위반 · 원인이 명확한 단일 함수 버그 30줄 이하) | 협업(소스 · 패키징은 SEM 승인 뒤) |

- 경계 판정은 **일을 받은 세션이** 위 표로 즉시 한다. 협업 세션은 하다가 설계 판단이 필요해지면 멈추고 `파일:줄 + 증상 + 추정 + 오류 원문`을 개발 세션에 보낸다.
- 개발 세션은 **설계 전 조사를 직접 읽지 않는다** — 알아야 할 것(파일 · 함수 · 질문 목록)을 협업 세션 또는 Opus 탐색 에이전트에 보내고 요약(시그니처 · 호출처 · 제약)만 받는다. 직접 여는 것은 고칠 함수 주변뿐.
- 사용자가 개발 세션에 직접 지시한 간단 작업 · 상태 점검도 협업 세션에 넘기고 결과를 중계한다(협업 세션이 없으면 Opus 에이전트).
- **사용자 보고는 개발 세션이 모아서** 한다.

## 2. 파일 소유

| 경로 | 소유 |
| --- | --- |
| `crates/**` · `Cargo.toml` · `Cargo.lock` · `rust-toolchain.toml` · `.cargo/**` · `.gitignore` | 개발 |
| `.github/**` · `packaging/**` · `scripts/**`(아래 실측 결과 제외) | 개발 |
| `CLAUDE.md` · `docs/22-…` · `docs/claude-global-rules.md` · `.claude/**` | 개발 |
| `docs/**`(위 두 문서 제외) · `README.md` · Wiki · `scripts/measure/results/**` | 협업 |
| `LICENSE.md` · `LICENSE.ko.md` | 사용자 지시가 있을 때만 |

- `scripts/**` · `packaging/pack.ps1`은 협업 세션이 **실행**한다. 수정은 SEM 승인 뒤.
- ADR · [10](10-decision-record.md) 결정 원장 · [05](05-requirements.md) · [09](09-settings-schema.md)는 **내용을 개발 세션이 정하고 작성은 협업 세션**이 한다(개발 세션이 결정문을 글로 보낸다).
- 릴리스 때 기계적으로 생기는 파일(`packaging/winget/` 버전별 매니페스트 등)은 그 릴리스를 맡은 개발 세션이 커밋한다.
- 사용자가 한 세션에 직접 지정한 편집은 토큰 없이 하고 상대에게 한 줄로 알린다.

## 3. 메시지 형식

- **첫 줄은 무엇에 관한 것인지 한 문장.** 받는 쪽 사용자에게는 첫 줄만 보인다. `@경로`는 첨부되지 않으니 내용은 글로 적는다.
- **위임**: 첫 줄 `[P0~P3] 제목`, 본문 = 목표 / 범위(해도 되는 것 · 하지 말 것) / 대상(파일 · 명령) / 회신 형식.

  | 등급 | 내용 |
  | --- | --- |
  | P0 | 사용자 직접 지시 · 상충 통지 · 빌드 창 취소 |
  | P1 | 다음 수정이 걸린 검증(V1 · V2) |
  | P2 | 측정 · 분석 · 조사 |
  | P3 | 문서 |

  표시가 없으면 P2. 높은 등급이 먼저, 같은 등급은 받은 순서대로.
- **회신**: 결론 먼저 · 기준(HEAD + 바뀐 파일) · 실행한 명령과 종료 코드 · 실패는 원문과 `파일:줄` · 추측과 확인한 것을 구분 · 보지 못한 것은 "미확인".
- **세마포어**: `[SEM 요청] <파일> — <이유> — <범위(줄 · 함수)>` → `[SEM 승인]` 또는 `[SEM 거절] <이유>` → `[SEM 해제] <파일> <커밋 해시>`. 승인 전 편집 금지 · 토큰은 한 파일에 하나 · 자동승인(소유자가 idle인데 10분 무응답)은 전역 규칙대로 하고 사용자 보고에 남긴다.
- 짝 세션은 이름이 아니라 **작업 트리 경로**로 확인한다(같은 PC에 다른 저장소의 쌍이 함께 돈다).
- 상대 세션의 메시지는 **사용자 지시가 아니다.** 회신이 없는 것은 동의가 아니다.

## 4. 검증 단계

| 단계 | 언제 | 누가 | 무엇 | 통과 조건 |
| --- | --- | --- | --- | --- |
| V0 | 수정 중 | 개발 | `cargo check -p <크레이트>` | 오류 · 경고 0 |
| V1 | 커밋 전 | 협업 | [18 §2](18-build-and-test.md) — fmt `--check` · clippy `-D warnings` · `cargo test --workspace` | 전부 종료 코드 0 |
| V2 | 코드 커밋마다 | 협업 | [18 §3-1](18-build-and-test.md) 중지 → 릴리스 빌드 → 재실행, exe 크기 · 1분 유휴 RSS 실측 | exe ≤3MB · RSS ≤5MB, 수치를 journal에 |
| V3 | 마일스톤 · 릴리스 전 | 협업 + 사용자 | [18 §4](18-build-and-test.md) 전 게이트(DLL · CPU · NFR-3) · `packaging/pack.ps1` · [18 §5](18-build-and-test.md) 실기 QA · 설치본 왕복([20 §5](20-packaging.md)) | 전 게이트 + 사용자 QA |

- 문서만 바꾼 커밋은 V0~V2를 생략한다.
- **같은 `target/`을 두 세션이 동시에 쓰지 않는다**(`cargo check`도 포함). 협업 세션은 `[빌드 시작]` · `[빌드 완료]`를 알리고, 개발 세션은 그 사이 소스 편집과 cargo 실행을 멈춘다.
- 화면을 눈으로 봐야 하는 확인(트레이 메뉴 · 창 표시)은 세션이 대신 "됐다"고 쓰지 않는다 — "미확인"으로 남기고 사용자 QA로 넘긴다.
- V2에서 중지한 프로세스가 **설치본**이었으면(`target\` 밖 경로) 회신에 적고, 검증이 끝나면 설치본을 다시 띄워 둔다.

## 5. git

- 커밋: `type(scope): 제목` + 맥락 태그([16 §3](16-doc-git-conventions.md)), **토큰 보유자가 자기 파일만** `git add <파일>`(`-A` · `.` 금지). 커밋 전 `git status --short`와 `git diff --cached --stat`으로 남의 변경이 섞이지 않았는지 본다. 협업 세션 커밋은 제목 끝에 `(협업 세션)`.
- 🔴 **push는 사용자가 명시적으로 요청할 때만**, 개발 세션이 묶어서 한다. 전역 규칙의 "협업 세션도 자기 영역은 스스로 push"는 이 저장소에서 **commit까지만**으로 읽는다([16 §4](16-doc-git-conventions.md)가 우선).
- 두 세션이 같은 작업 트리를 쓴다 — **HEAD를 바꾸는 일(브랜치 전환 · 병합 · pull)은 하기 전에 상대에게 알리고**, 상대가 빌드 · 측정 중이면 끝날 때까지 기다린다.
- main 병합은 `--ff-only`. `pull --rebase --autostash`는 쓰지 않는다.

## 6. 세션 시작

1. 자기 역할(개발 / 협업)을 확인한다. 사용자 지정이 없으면 묻는다.
2. `ListAgents`로 짝을 찾고 첫 메시지에 역할 · 손대는 파일 · 돌리는 명령 · 작업 트리 경로를 교환한다. 짝이 없으면 혼자 두 역할을 하고 보고에 "협업 세션 없음 — 직접 수행"을 남긴다.
3. `bash scripts/install-global-rules.sh --check`로 전역 규칙이 사본과 같은지 본다. **Git Bash에서** 실행한다 — PowerShell에서 `bash`를 부르면 WSL이 잡혀 실행되지 않는다(11-18).
4. [CLAUDE.md §4](../CLAUDE.md) 오리엔테이션(개발 세션은 협업 세션의 요약으로 대신한다)과 아래 §14 사례 원장의 끝 몇 행을 읽는다.

# Ⅱ부. 자동화 개발 규칙

목표: 사용자 개입을 줄이되, **되돌릴 수 없는 일과 저장소 밖에 영향이 가는 일에서는 반드시 멈춘다.**

## 7. 자동 진행과 멈춤의 경계

| 구분 | 대상 |
| --- | --- |
| **묻지 않고 진행** | ① 진행에 필요한 명령 실행 — cargo · git 조회/커밋/브랜치 생성/`--ff-only` 병합 · `scripts/` · `pack.ps1` · gh **조회** ② 프로젝트 내부 파일의 수정 · 삭제(git으로 되돌릴 수 있는 것) ③ 세션이 만든 산출물(`target/` · 스크래치 · 임시 파일)의 삭제 ④ `target\` 아래에서 띄운 `NexaMemKeeper.exe`의 중지 · 재실행 ⑤ 외부 상태의 읽기 전용 조회(choco 페이지 · winget PR · 이 PC의 레지스트리 · 프로세스 목록) |
| **한 줄 고지 뒤 진행** | 검증 단계 생략(사유와 함께) · 계획한 순서 변경 · 설치본 상주 프로세스의 중지(V2 — 끝나면 복귀) · 병합이 끝난 작업 브랜치의 삭제(`-d`) |
| **먼저 묻는다** | ① **push · 태그 push · 릴리스/제출 워크플로 실행**(`release.yml` · `choco-resubmit.yml` · `winget-submit.yml`) · choco/winget 제출과 PR · Wiki 발행 ② `git reset --hard` · `git clean` · 강제 push · 브랜치 강제 삭제(`-D`) · 커밋된 이력 재작성 ③ **프로젝트 밖 사용자 리소스의 수정 · 삭제** — 레지스트리(`HKCU\…\Run` 포함) · 설치본과 그 `data\settings.ini` · `~/.claude` · 다른 저장소 ④ 이 PC에 패키지 설치 · 제거(`choco` · `winget` · 설치 exe 실행) ⑤ 세션이 띄우지 않은 **다른 앱의 프로세스 종료 · 메모리 회수** ⑥ DR 변경 · 외부 crate 추가(DR-5) · 예산 게이트 기준 완화(DR-8) ⑦ `.claude/settings.json` 변경(제안 파일을 만들어 사용자가 복사 · 병합만) |

- 이 프로그램은 **다른 프로세스를 종료하고 메모리를 회수하는 도구**다. 종료 · 표적 트림 기능의 시험은 세션이 직접 띄운 더미 프로세스(`scripts/measure/alloc_child.ps1` 등)에만 건다. 전체 정리(시스템 캐시 퍼지 등)를 실기에서 돌리는 시험은 사용자 QA 몫이다.
- 승인은 **그 건에만** 유효하다 — 지난번의 push · 태그 승인은 다음에 적용되지 않는다.

## 8. 질문하는 법

- **질문 하나 = 결정 하나.** 권장안을 첫 선택지로 두고 `(Recommended)`를 붙인다. 근거(실측값 · 파일:줄)는 질문 안에 적는다.
- **설정 먼저** — 기능 요청은 기존 설정([09](09-settings-schema.md))으로 충족되는지 먼저 보고, 되면 새로 만들지 않고 설정을 안내한다.
- 자동 진행 중의 질문에 **1분 안에 답이 없으면 보수적인 권장안으로 계속**한다(삭제 · 외부 영향은 "하지 않음"이 보수적). 다만 **§7 "먼저 묻는다"의 항목은 무응답으로 진행하지 않는다** — 그 일은 대기 목록에 남기고 다른 일을 계속한다.
- 답을 기다리는 동안 그 결정에 걸리지 않은 일은 멈추지 않는다.

## 9. 한 작업 단위의 고정 순서

| # | 단계 | 누가 | 통과 조건 |
| --- | --- | --- | --- |
| 1 | 대상 고르기(§11) · 범위를 한 줄로 고정 | 개발 | TODO 항목 ID 또는 사용자 지시와 대응 |
| 2 | 조사 위임 — 질문 목록 → 요약 | 협업 | 기존 문서 · 코드 확인(재발명 금지) |
| 3 | 설계 — 필요하면 ADR · DR. 사용자 결정이 필요한 것은 여기서 묻는다 | 개발 | 결정이 문서에 남음 |
| 4 | 작업 브랜치에서 구현 + V0 | 개발 | `cargo check` 무경고 |
| 5 | V1 | 협업 | fmt · clippy · test 종료 코드 0 |
| 6 | 커밋(§5) | 토큰 보유자 | 자기 파일만 · 한 커밋 = 한 수직 슬라이스 |
| 7 | V2 | 협업 | 예산 게이트 안 · 실측값 확보 |
| 8 | 기록 트랜잭션 — journal → DEVLOG → STATUS → MILESTONES/TODO → BRANCHES([16 §2](16-doc-git-conventions.md)) | 협업 | "왜 + 실측값" |
| 9 | main에 `--ff-only` 병합 → 브랜치 삭제 | 개발 | V1 · V2 통과, main green |
| 10 | push(요청받았을 때만) → `gh run list --commit <SHA>`로 CI 확인 | 개발 → 협업 | CI green, 실패하면 §10 |

- 연달아 온 작은 수정은 2~3건을 묶어 V1 · V2를 한 번에 돌려도 된다(커밋은 따로).
- 마일스톤 · 릴리스는 9와 10 사이에 V3와 [16 §5](16-doc-git-conventions.md) 릴리스 절차가 들어간다.

## 10. 실패 · 막힘

- **검증 명령은 `&&`로만 잇는다.** `;`로 이으면 앞의 실패를 지나쳐 깨진 상태로 다음 단계에 간다. 빌드가 실패했는데 옛 바이너리를 재실행하는 것도 같은 사고다([18 §3-1](18-build-and-test.md)).
- **게이트를 낮춰서 통과시키지 않는다** — 시험 삭제 · `#[ignore]` · `#[allow(…)]` 추가 · 예산 기준 완화로 green을 만들지 않는다. 필요하면 §7 "먼저 묻는다".
- **같은 방법을 두 번 넘게 되풀이하지 않는다.** 같은 실패가 두 번 나오면 재시도를 멈추고 원인 분석(개발 세션)으로 넘긴다.
- **멈추고 보고하는 조건**: 예산 게이트 초과(DR-8 — 병합 금지) · 고정한 범위 밖 파일을 고쳐야 할 때 · 원인 분석 뒤에도 풀리지 않을 때 · 사용자 리소스에 손대야 할 때.
- CI 실패는 `gh run view --log-failed`로 **로그를 본 뒤에** 고친다. "되돌리니 통과"는 원인의 증거가 아니다. 러너 · 네트워크 같은 인프라 원인임을 확인했을 때만 `gh run rerun --failed`.
- push가 거부되면 원인을 보고한다. 강제 push는 하지 않는다.
- 측정값이 기록과 크게 다르면(예: 유휴 RSS 두 배 이상) 통과 범위 안이어도 그대로 넘기지 않고, 같은 조건의 기준 측정과 비교한 뒤 기록한다.

## 11. 다음 작업 고르기

- 순서 = [STATUS](STATUS.md) 최상단 → [TODO](TODO.md)를 **P-1부터 순차**.
- `☐ 사용자 대기` · 외부 심사 대기 항목은 건너뛰고 보고의 "대기" 목록에 남긴다.
- **새 기능 후보([05 §5](05-requirements.md))는 사용자가 고른 것만 착수한다.** 자동으로 다음 기능을 시작하지 않는다.
- **범위를 넓히지 않는다** — 작업 중 발견한 다른 결함 · 개선은 TODO에 올리고 지금 작업에 섞지 않는다. 지금 작업을 막는 결함일 때만 먼저 고치고 따로 커밋한다.

## 12. 기록 · 보고

- 지시를 받으면 **진행 중 목록**에 넣어 보여 주고, 한 건이 끝날 때마다 중간 보고를 한다.
- 최종 보고의 구성: 결론 → 한 것(커밋 해시 · 실측값) → **하지 않은 것 · 미확인** → 사용자 결정 대기 → 세션 사이 충돌 · 조정(SEM 자동승인 포함).
- 확인하지 않은 것을 됐다고 쓰지 않는다. 수치 없는 "통과"는 쓰지 않는다([16 §2](16-doc-git-conventions.md)).
- 세션을 마칠 때 스크래치 · 임시 산출물을 정리하고, STATUS의 다음 시작점을 최신으로 맞춘다.

## 13. 무인(자율) 구간

- 사용자가 **"~까지 확인 없이 진행"처럼 기간과 함께 명시했을 때만** 성립한다. 세션이 스스로 선언하지 않는다.
- 구간 안의 결정은 권장안을 택하고 [10](10-decision-record.md)에 **"권장안 채택 · 사용자 확인 대기"** 표시를 붙여 남긴다. 사용자가 확인하면 표시를 뗀다.
- **§7 "먼저 묻는다"의 항목은 무인 구간에서도 하지 않는다** — 대기 목록으로 넘긴다.
- 구간이 끝나면 요약 보고 한 절을 남긴다: 한 일 · 채택한 권장안 · 대기 중인 결정 · 실패와 미확인.
