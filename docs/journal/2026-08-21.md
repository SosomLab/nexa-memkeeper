## 2차 — 승인 가능성 재검토 (사용자 요청)

1차 수정 뒤 "승인에 문제가 없는지" 다시 점검했다. chocolatey **모더레이션 기준 문서**와
**76개 validator 규칙(CPMR0001~0076)** 목록을 받아 우리 제출물과 하나씩 대조했다.
정리는 [20 §7-9](../20-packaging.md)에 표로 남겼고, 여기에는 판단 근거만 적는다.

### 1차 수정이 **문서화된 규칙 위반**이었음을 확인

> "PowerShell scripts need to be saved in **UTF-8 with BOM**. PowerShell is ignoring the
> standards and needs a BOM in order to recognize scripts as UTF-8. Otherwise it processes
> non ASCII characters incorrectly." — [create-packages](https://docs.chocolatey.org/en-us/create/create-packages/)

우리 `.ps1` 3개가 전부 BOM 없는 UTF-8이었다. 즉 1차 수정은 "그러면 좋은 것"이 아니라
**공식 문서가 요구하는 것**이었다. 제거 실패도 모더레이터 확인 항목에 그대로 있다 —
*"Does the package uninstall correctly? (this means the package, not the underlying
software.)"* 괄호가 정확히 우리 경우(패키지 스크립트 실패)를 가리킨다.

### 기우로 판명된 것 — 패키지 이름 구조

`nexa-memkeeper`(설치형) + `nexa-memkeeper.portable` 조합이 규약 위반이 아닌지 의심했다.
브랜드 신규 패키지는 **이름이 규약에 어긋나면 즉시 거부(rejecting immediately)** 대상이라
확인이 필요했다. 결과: 기준 문서는 *"flag on '.' in name (**unless .portable/.install**)"*뿐이고,
바깥 id를 메타 패키지로 만들라는 요구는 **어디에도 없다**. 위험 없음.

### 새로 고친 것 — 설치형의 `portable` 태그

설치형 nuspec의 태그에 `portable`이 들어 있었다(포터블 nuspec을 복사한 흔적). 요구사항의
*"The tags field is not being abused"*에 걸릴 수 있고 사실과도 다르다 → 제거.

### 확인만 하고 넘어간 것

- **다운로드 출처**: 기준은 *"Use the project site (projectUrl) to determine where the download
  … is coming from and it should match the one in the package files."* `sosomlab.com` →
  `/apps/nexa-memkeeper` → GitHub Releases(0.7.0 포함) 링크가 실제로 있다(실측). 다만 사이트가
  한국어라 모더레이터가 두 번 눌러야 한다 — 바꿀 만한 문제는 아니라고 봤다.
- **VirusTotal 1~5건**(설치형): chocolatey-ops가 *"not enough detections to prevent the
  approval"*로 못 박았다. 무서명 + 메모리 조작 도구의 통상 오탐.
- **`license` 태그**(Guideline): 상업용만 유료라 애매하다. Guideline은 승인을 막지 않으므로 보류.
- **winget**: 매니페스트 자체는 자동 검증을 통과했고 조치 라벨이 없다. 막을 요소 없음 — 큐만 남았다.

### 🔴 발견 — `choco uninstall nexa-memkeeper`는 **항상 실패한다**

검증 요약([gist](https://gist.github.com/choco-bot/17ec5547b6e45b7b7c235f82c0a1ae62))이
설치형만 이렇게 적혀 있었다:

```
 * Install was successful.
 * Uninstall failed (allowed). Note that the process may have hung, ...
```

`Uninstall.txt`를 열어 보니 원인이 분명했다.

```
ERROR: At ...\chocolateyuninstall.ps1:10 char:18
+   Write-Warning "$packageName: ...
Variable reference is not valid. ':' was not followed by a valid variable name character.
```

- `"$packageName: …"`에서 PowerShell은 `$packageName:`을 **스코프 한정 변수**(`$env:PATH` 꼴)로
  읽는다. 뒤에 오는 한글은 변수명이 될 수 없어 **파싱 단계에서 실패**한다.
- 파싱 실패이므로 분기와 무관하게 **스크립트 전체가 실행되지 않는다**. exit `-1` → choco가
  패키지를 `lib-bad`로 옮기고 롤백. 즉 `choco uninstall`은 **한 번도 성공한 적이 없다**.
- 로컬 재현: `Parser::ParseFile` → **오류 2건**(line 10·14). 수정 후 **0건**.

### 곁가지 — BOM 없는 UTF-8이면 한글이 깨진다

같은 로그의 한글이 `ì œê±°`로 찍혔다. chocolatey 검증기는 스크립트를 **Windows PowerShell
5.1**로 돌리는데, 5.1은 **BOM 없는 .ps1을 시스템 ANSI 코드페이지로 읽는다**. 구문을 고쳐도
경고 문구가 깨진 채 나갔을 것이다. → 패키징 `.ps1` 4개 전부 **UTF-8 BOM**으로 통일.

`release.yml`·`choco-resubmit.yml`의 `Set-Content $ps1 -NoNewline`은 pwsh 7 기본값이
`utf8NoBOM`이라 **팩 시점에 BOM을 도로 벗긴다**. `-Encoding utf8BOM`을 붙여 막았다.

### 검증

Windows PowerShell 5.1(`powershell.exe`)로 스텁을 물려 세 분기를 모두 태웠다.

| 분기 | 결과 |
| --- | --- |
| 등록 항목 0개 | `WARNING: nexa-memkeeper: 제거 항목을 찾지 못했습니다(이미 제거됨).` · exit 0 |
| 등록 항목 1개 | `File=[C:\Program Files\Nexa MemKeeper\unins000.exe]` 정상 전달 · exit 0 |
| 등록 항목 2개 이상 | 목록 경고 후 건너뜀 · exit 0 |

한글도 정상 출력됐다(BOM 효과).

> `-File $key.UninstallString.Trim('"')`은 **정상**이다. Inno는 `UninstallString`에 인자 없는
> 따옴표 경로만 쓰고 `/SILENT`는 `QuietUninstallString`에 넣는다. 검증 스냅샷 XML의
> `<UninstallString>`에 `/SILENT`가 보이는 건 choco 자신의 직렬화 형식이다.
