## 13차 — 권한 실측 답변 · 의사 프로세스 숨김 옵션 (사용자 문의/요청)

**질문 1: "관리자 권한으로 실행되어야 하나? 자동 시작되면서 설정이 가능한가?"** → 같은 PC에서 승격/비승격을 연속 실행해 실측하고 [07 §4](../07-adr-0002-memory-reclaim.md)에 표로 기록.

| | 일반 권한(제한 토큰) | 관리자 승격 |
| --- | --- | --- |
| 워킹셋 트림 | 115개 성공 / 378 제외 | **466개** / 25 제외 |
| 영역② 스탠바이 퍼지 | `0xC0000061`(PRIVILEGE_NOT_HELD) 실패 → partial | NTSTATUS 0 성공 |
| 회수량 | **+322MB** | **+847MB**(2.6배) |

→ **관리자 권한은 필수가 아니다.** 일반 권한으로도 관찰·목록·자기 세션 트림이 동작하고 실제로 회수된다. 승격은 "더 많이" 회수하기 위한 선택지이며, 생략된 영역은 알림에 명시된다.
자동 시작과 권한 관계도 [07 §4-1](../07-adr-0002-memory-reclaim.md)에 정리: 현재 구현(`HKCU\…\Run`, DR-11)은 **일반 권한 시작**이고 Windows 정책상 Run 키로는 승격이 불가능하다. 승격 자동 시작이 필요하면 **작업 스케줄러 "가장 높은 수준의 권한으로 실행"**이 표준 해법(FR-6에 계획, 미구현).

**요청 2: "의사 프로세스도 숨기는 옵션을, 기본은 숨김으로"** → 구현.
- mk-core `is_pseudo`/`filter_pseudo` + 테스트(숨김 대상 = Memory Compression·MemCompression·Registry·Secure System / **System·System Idle Process는 제외** — 작업 관리자도 이 둘은 표시한다). 테스트 **23 green**.
- 메인 화면 설정 메뉴에 **"의사 프로세스 숨기기"** 체크(기본 on), 끄면 즉시 목록 재구성. Top 5 팝업도 같은 규칙으로 숨김.

**교훈(재기동 절차 정정)**: 실행 중인 exe를 Windows가 잠그므로 `cargo build --release`를 먼저 하면 `os error 5`로 링크 실패한다. 더 위험한 건 **빌드 실패를 놓치고 옛 바이너리를 재실행**하는 것(이번에 실제로 한 번 발생 — 재기동은 됐으나 새 기능이 없는 바이너리였다). → [18 §3-1](../18-build-and-test.md) 절차를 **중지 → 빌드 → 실행** 순서로 정정.

## 12차 — 메인 화면(트리 그리드)·알림 이름·메뉴 정리 (사용자 요청 5건 연속)

**사용자 요청**: ① 알림에 `mk-app.exe` 대신 제품명 표시 ② 우클릭 "Top 5 보기"는 좌클릭과 중복 → "목록 보기"로 바꾸고 **전체 목록** 표시 ③ 좌클릭 팝업 버튼은 **지금 정리·목록 보기 2개만**(설정은 우클릭 전용) ④ 목록 창이 **메인 화면** — 상단 메뉴(환경 설정·자동 실행 등) + **그리드·헤더 클릭 정렬** ⑤ 좌측 확장 버튼으로 **쓰레드·프로세스 트리** 전개 + **프로세스/트리/쓰레드 종료**.

**구현**:
- **DR-12 알림 이름**: 빌드 스크립트(`build.rs`)가 Windows SDK `rc.exe`를 직접 찾아 VERSIONINFO를 임베드(외부 crate 0 — DR-5 유지, rc.exe 없으면 조용히 건너뜀). 배포 파일명도 `NexaMemKeeper.exe`로 변경(`[[bin]] name`). 실측: `FileDescription = Nexa MemKeeper` 확인.
- **DR-10 메인 화면**(`listwnd.rs`): 메뉴바 4개(파일/메모리/설정/도움말) · 트리 그리드(교대 행·구분선·정렬 화살표 ▲▼) · 확장 버튼 ▸/▾ · 쓰레드 행(TID·상태·컨텍스트 전환) · 스크롤바+휠 · 상태 줄 · 1·2·5초 갱신 주기 선택.
- **종료 3종**: 프로세스(2단계) · **프로세스 트리**(자손을 잎부터 역순 종료 — 부모가 죽는 사이 자식이 되살아나는 것 방지) · **쓰레드**(경고 문구 포함 확인). 보호 대상은 메뉴가 비활성.
- **DR-11 자동 실행**: 설정 메뉴 토글 → `HKCU\…\Run`에 값 1개(따옴표로 감싼 exe 경로). 끄면 삭제. 포터블 원칙의 명시적 예외로 문서화.
- mk-core에 트리 로직 이관(테스트 가능): `build_rows`(펼침 상태 반영 평면화·고아 보존·**순환 보호**), `descendants`, `sort_procs`, `ThreadInfo` — **테스트 22 green**.
- 열거 확장(`procs.rs`): 같은 버퍼에서 부모 PID(`Reserved2`)와 **쓰레드 배열**까지 파싱. `SYSTEM_PROCESS_INFORMATION`=256B·`SYSTEM_THREAD_INFORMATION`=80B를 **컴파일 타임 크기 단언**으로 고정하고, 버퍼 잔여 길이로 쓰레드 개수를 잘라 경계를 지켰다.

**실측**: exe **0.41MB** · 상주 셸 유휴 **1.71MB** · 열거 500 프로세스 **7.5ms**(디버그) · 목록 창(워커) 열림 시 14.79MB → **닫으면 프로세스 종료로 전량 회수**(하이브리드 구조 DR-7의 실효 확인).

**사용자 질문 "Memory Compression 뭐야? 작업 관리자 목록과 왜 다르지?"** → 조사 결과를 [19 §4-5](../19-memory-measurement-and-reclaim.md)에 문서화. 요지: ① 압축 메모리 저장소 프로세스(WS 1,413MB / 프라이빗 바이트 10MB) ② 작업 관리자 **자세히** 탭이 의사 프로세스를 숨기는 것(PowerShell·Process Explorer에는 보임 — 우리 열거 500개 vs `Get-Process` 499개로 동일) ③ 정렬 지표 차이(우리=프라이빗 워킹셋, 작업 관리자=작업 집합) — `rust-analyzer`가 프라이빗 1,440MB/WS 503MB로 순위가 뒤집히는 실례. **버그 아님**.

## 11차 — M2 Top 5 팝업 구현·실측 (사용자 요청 "다음 진행")

**무엇**: `feat/m2-top5-popup` → main 병합(`b84cbdd`). 트레이 좌클릭 팝업 + 항목 조작.

**규약 정정 먼저**: [15 §4](../15-dev-methodology.md)의 "미문서 NT API는 셸 금지"가 [ADR-0003 §3](../08-adr-0003-resident-architecture.md)(Top 5 팝업을 셸에 배치)과 충돌 → **읽기 전용 조회는 셸 허용**으로 정정. 근거: 부작용이 없고, 팝업 즉시성(NFR-4 <100ms)에 워커 spawn을 낄 수 없다. 대신 **버퍼 워킹 경계 검사 의무화**(오프셋 전진·구조체 크기·문자열 길이 검증, 손상 시 조기 중단). 상태 변경(OpenProcess·트림·종료·NtSetSystemInformation)은 그대로 워커 전용.

**구현**: `procs.rs`(열거 1콜) · `popup.rs`(380×230 커스텀 드로잉 — 요약+사용률 바·Top 5 행·버튼 3·호버·더블버퍼·포커스 상실 시 닫힘·닫을 때 자기 트림) · 항목 우클릭 → 트림/종료(확인 후) → 워커 위임 · `worker`: `run_trim`/`run_kill`(WM_CLOSE 3초 대기 후 TerminateProcess).

**실측**:
- 열거: **482 프로세스 6.5ms**(디버그 빌드) — NFR-4 예산 100ms 대비 15배 여유.
- 릴리스: exe **0.36MB** · 유휴 RSS **2.23MB** → 팝업 열림 **6.94MB** → 닫은 후 **0.74MB**. **NFR-3(유휴 복귀) 확인** — 자기 트림 덕에 오히려 초기 유휴보다 낮아졌다.

**교훈(테스트 스크립트 함정)**: 트레이 콜백은 `WM_APP+1 = 0x8001`인데 검증 스크립트가 `0x0401`(WM_USER+1)로 보내 "팝업이 안 뜬다"고 40분 헤맸다. **코드가 아니라 테스트가 틀린 경우** — 진단 로그(`shell: WM_TRAY event=…`)를 넣고 나서야 메시지 자체가 도착하지 않았음이 드러났다. 디버그 빌드에 남겨 둔다.

**보호 목록 보강**: 커널이 보고하는 실제 이름이 `Memory Compression`(작업 관리자 표기와 동일)이라 기존 `memcompression` 항목으로는 매칭되지 않았다 → 두 표기 + `System`·`System Idle Process` 추가.

**무엇**: `feat/m1-clean-engine` → main 병합. 워커 프로세스 정리 엔진 + 셸 연동.

**구현**:

- `shell.rs`: "지금 정리"(실행 중 회색), "관리자 권한으로 재시작"(`ShellExecuteW runas` — 비승격일 때만 표시), 워커 완료 풍선 알림, 툴팁 둘째 줄(마지막 정리 MB·경과), 정리 직후 아이콘 즉시 갱신.
- `mk-core`: 보호 목록 판정(`is_protected`)·워커 결과 프로토콜(종료 코드 = 회수MB | PARTIAL 비트)·알림 문구 — **테스트 11 green**.
- 격리(DR-7): 워커는 별도 스레드가 `Command::status()`로 대기 후 `PostMessage` — 크래시 시 `WORKER_ERR`로 실패 통지, 셸은 생존.

**실측(진단 stderr 1줄 추가 — 콘솔 실행 시만 노출)**:
```
clean: trimmed=461 skipped=25 purge_status=0x00000000 avail 6782MB -> 6991MB (+209MB)
2회차: +44MB   ← 이미 정리된 상태라 감소, 정상 동작
```
- 예산 재측정: **exe 0.34MB ≤3 · 유휴 RSS 2.20MB ≤5 · CPU 0.062s/60s** · 임포트 OS 인박스 8종(advapi32 추가 — 토큰 특권). 전 게이트 유지.

**교훈 2건**:
1. **PowerShell로 GUI 서브시스템 exe의 종료 코드를 못 잰다** — `& $exe`가 대기하지 않아 항상 0. 릴리스 빌드 검증은 디버그 빌드(콘솔 있음)로 하거나 `Start-Process -Wait` 필요. 셸의 `Command::status()`는 서브시스템과 무관하게 정상 대기.
2. **영역②(스탠바이 퍼지)는 `Available` 수치를 올리지 않는다** — Standby도 Free도 모두 Available에 포함되므로(docs/19 §2-1) 퍼지는 Available 내부 이동일 뿐. 보고된 +209MB는 **영역①(트림)의 성과**다. 회수량 수식(docs/19 §4-3 = Avail 델타)은 트림 효과를 정직하게 반영하므로 유지 — 숫자 부풀리기가 없다는 점에서 오히려 적합.

## 3차 — 판단 우선순위 확정(DR-4) → ADR-0003 권고 정정 (사용자 확정)

**무엇**: 사용자 지시 "개발·배포의 편의성보다 성능·동작 안정성이 더 중요" → **DR-4로 고정**([10 §1](../10-decision-record.md)), [00 비전](../00-vision.md) 설계 원칙 0으로 반영.

**정정된 판정**:
- [ADR-0003](../08-adr-0003-resident-architecture.md): 단일 프로세스 권고 → **하이브리드 권고로 정정**. 최초 A 우위 근거가 "IPC 복잡도"(= 개발 편의)였는데 DR-4 기준상 무효 — B의 100% 회수 보장·크래시 격리(안정성)가 우선. 성능 열세(워커 spawn ~50-150ms)는 즉시성이 필요한 Top 5 팝업만 셸에 남겨 소거. 원래 판정문은 취소선 보존(규칙 5).
- [ADR-0001](../06-adr-0001-stack.md): 권고 A(Rust) 유지·논거 강화 — C/C++ 대비 우위 축을 개발 편의가 아닌 **안정성**(수동 메모리 관리의 크래시 면적 vs 컴파일 타임 안전)으로 재정리. C#/Go 탈락 사유에 GC 정지·점유 변동(안정성) 추가.

**부수 이득 기록**: 하이브리드 구조에서 승격 필요 정리 영역(②~⑥)은 워커만 승격 가능 — 상주 셸은 항상 일반 권한 유지(08 §4-5).

## 2차 — 개발 목표·기술 기반 문서화 (사용자 요청)

**무엇**: 사용자가 프로그램 목적을 확정 제공(DR-3) → 지식 문서 5건 작성.

- [00 비전](../00-vision.md) — 목적(사용자 원문 반영)·설계 원칙 5·예산 제안(유휴 RSS ≤5MB·exe ≤3MB·DLL 0 — ☐ 확정 대기).
- [05 요구사항](../05-requirements.md) — FR-1~6(트레이 셸·Top 5 팝업·프로세스 트리 뷰(쓰레드)·정리 엔진·설정·권한) / NFR-1~5 게이트 / **참조 프로그램 차용표**(Mem Reduct·Windows Memory Cleaner·RAMMap·Wise MO) / **설정 스펙+추천 기본값**(임계값 90%·쿨다운 5분·안전 영역만 기본 on·보호 프로세스 고정 목록).
- [06 ADR-0001 스택](../06-adr-0001-stack.md) — 후보 5안(Rust/C·C++/C#/.NET·NativeAOT/Go) 비교. **권고 A: Rust+windows-rs** — C#·Go는 유휴 RSS가 예산의 3~15배로 목적 모순, Rust는 nexa-dir2 실증 자산(ctl·CI·패키징) 재사용.
- [07 ADR-0002 회수 기법](../07-adr-0002-memory-reclaim.md) — 관찰(GlobalMemoryStatusEx 5초 폴링+이벤트 옵션)·열거(NtQuerySystemInformation 1콜로 프로세스+쓰레드+프라이빗 워킹셋)·회수 영역 ①~⑥ API 매핑(EmptyWorkingSet·NtSetSystemInformation SystemMemoryListInformation 계열)·권한 전략(asInvoker+승격 재시작+작업 스케줄러)·폴백.
- [08 ADR-0003 상주 구조](../08-adr-0003-resident-architecture.md) — 단일 프로세스+지연 로드+자기 트림(권고) vs 셸/워커 분리. 기능부가 작아 IPC 복잡도가 이득 초과 — 단, NFR-3 실측 실패 시 B 전환 조건 명기.

**왜 이렇게**: 사용자 지시 "각 기술의 장단점을 정리해서 보고 판단할 수 있도록" — 결정 3건(스택·기법·구조)을 전부 📐 제안 상태로 두고 권고+되돌림 조건만 명시. 확정은 사용자 판단 후 DR-4~7로 승격.

**리스크 기록**: NtSetSystemInformation은 미문서 API지만 RAMMap(MS Sysinternals) 동일 경로 — 사실상 준표준으로 판단, 버전 가드+폴백 정의(07 §5).
