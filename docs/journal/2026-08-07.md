## 37차 — `0.6.1` 자산 누락 수정 · winget 포터블 패키지 추가 (사용자 요청)

**🐛 `0.6.1`에 설치본 ZIP이 빠졌다.** `pack.ps1`은 제대로 만들었지만(SHA256SUMS에 3줄이 들어간 것으로
확인), **워크플로의 첨부 목록에 그 줄이 반영되지 않았다** — 앞선 편집 스크립트가 문법 오류로 중간에
죽었는데 pack.ps1만 다시 고치고 release.yml은 놓친 것. 태그 시점 파일을 열어 보고서야 드러났다.
교훈: **자산 목록은 릴리스 결과로 검증**해야지 스크립트가 "성공"했다고 믿으면 안 된다.

**winget 포터블 패키지**(사용자 요청) — winget은 한 패키지에 설치형과 포터블을 함께 담을 수 없다.
자산·설치 방식·설치 범위가 모두 다르기 때문이다. 그래서 둘로 나눴다.
| 패키지 | 형식 | 범위 |
| --- | --- | --- |
| `SosomLab.NexaMemKeeper` | `inno` (+ `/ALLUSERS`) | machine |
| `SosomLab.NexaMemKeeper.Portable` | `zip` + `NestedInstallerType: portable` | user |

포터블은 ZIP 안의 `NexaMemKeeper.exe`를 **`nexamemkeeper` 명령 별칭**으로 등록한다(승격 불필요).
릴리스 워크플로는 게시가 켜졌을 때 두 패키지 각각에 PR을 만든다. 매니페스트는 패키지별 폴더로 분리했다.

**요청**: "github action 에서 빌드 되도록 배포 구성해줘" → "winget 과 choco에 등록이 가능하도록 솔루션

**워크플로 2종** — [ci.yml](../../.github/workflows/ci.yml)(push·PR: fmt·clippy·test + 예산 게이트),
[release.yml](../../.github/workflows/release.yml)(태그 push: 포장 → Release 자산 첨부).
게이트를 CI와 로컬이 **같은 `pack.ps1`**로 태우는 게 핵심 — 기준이 두 곳으로 갈라지지 않는다.

**게시 스위치(사용자 지시)** — `nexa-dir2`와 같은 방식으로, 저장소 변수 + 시크릿이 **둘 다** 있을 때만
게시한다. 지금은 변수가 없으므로 **choco nupkg는 만들되 push하지 않고**, winget PR도 열지 않는다.
| 채널 | 조건 | 꺼진 상태 |
| --- | --- | --- |
| Chocolatey | `vars.CHOCO_PUSH == 'true'` + `secrets.CHOCO_API_KEY` | nupkg만 만들어 아티팩트로 남김 |
| winget | `vars.WINGET_PUBLISH == 'true'` + `secrets.WINGET_TOKEN` | 아무것도 하지 않음 |

**패키지 자산** — choco 2종(`nexa-memkeeper` 설치형 / `.portable`)과 winget 매니페스트 3종.
바이너리는 **동봉하지 않고 Release 자산을 URL+SHA256으로 참조**한다(PolyForm NC = 비-FOSS라
커뮤니티 저장소 재배포 규정상 공식 URL 다운로드가 정석). `{{VERSION}}`·`{{CHECKSUM64}}`는 릴리스
워크플로가 태그 시점에 치환한다.

> ⚠️ **`/ALLUSERS`가 필요한 이유**: 패키지 매니저는 승격된 세션에서 조용히 설치한다. 우리 설치기는
> 기본이 사용자별이라 그대로 두면 **관리자 계정의 `%LOCALAPPDATA%`**에 깔려 정작 사용자에게는 보이지
> 않는다. `PrivilegesRequiredOverridesAllowed=commandline`을 열고 매니페스트가 `/ALLUSERS`를 넘긴다.
> 자동 실행은 `/TASKS=""`로 끄고 설치한다(설치 계정 ≠ 사용 계정일 수 있다).

**덤으로 잡은 것 — DLL 게이트가 그동안 안 돌고 있었다.** `dumpbin`을 PATH에서만 찾다 보니 늘 "건너뜀"
이었다. `vswhere`로 찾도록 고쳤는데, `-latest -products *`는 **VS 셸만 얹은 SSMS**를 집어 VC\Tools가
없었다 → `-requires Microsoft.VisualStudio.Component.VC.Tools.x86.x64`로 한정. 이제 실제로 돌아
**외부 DLL 0 확인**(kernel32·user32·gdi32·comctl32·shell32·advapi32·ntdll·oleaut32·version·
bcryptprimitives + api-ms 세트). `api-ms-win-*`는 API 세트라 접두사로 통과시키고, 재배포 런타임
(`vcruntime140.dll` 등)은 여전히 걸리도록 두었다.

**검증**: 워크플로 YAML·winget 매니페스트 파싱, nuspec XML 파싱, **로컬 `choco pack` 2종 성공**

## 32차 — M5-1 영역 ⑥ 페이지 결합 · 저메모리 이벤트 트리거

**영역 ⑥ 페이지 결합** — `NtSetSystemInformation(SystemCombinePhysicalMemoryInformation=130)`.
인자는 `MEMORY_COMBINE_INFORMATION_EX`(24바이트 — 크기가 틀리면 `STATUS_INFO_LENGTH_MISMATCH`)이고,
커널이 **결합한 페이지 수**를 돌려주므로 회수량을 그대로 보고에 싣는다. 실패하면 partial(조용한 성공 금지).

> 🔍 **예상과 달랐던 점**: ADR-0002는 ⑥을 "관리자 필요"로 적어 두었는데, **일반 권한에서도 NTSTATUS 0으로
> 성공**했다(Windows 11 26200 실측 — 349MB 결합, Available 3825MB → 4190MB, **+365MB**). 문서의 권한 열을
> "관리자(권장)"로 정정하고 실측치를 남겼다. 소요는 수 초라 워커에서 도는 구조(DR-7)가 그대로 유효하다.

**저메모리 이벤트 트리거** — `CreateMemoryResourceNotification(LowMemoryResourceNotification)` 핸들을
한 번 만들어 두고 **폴링 때마다 질의**한다. 대기 스레드를 쓰지 않은 이유: 스레드 하나가 유휴 예산(DR-8)을
갉아먹는데, 질의는 커널 플래그를 읽는 수준이라 이미 도는 타이머에 얹는 편이 싸다.
판정은 `should_auto_clean_with()` 한 곳에 모았다 — 이벤트가 켜져도 **쿨다운은 지킨다**(부족 상태는 한동안
계속 켜져 있어서, 안 그러면 폴링마다 정리가 반복된다). 설정 `auto.low_memory_event`(기본 on) + 설정 창 체크박스.

**설정 창**: 자동 정리 그룹에 체크박스 1줄이 늘어 창 높이 602 → 628, 아래 그룹·버튼을 26px씩 내렸다.
자식 컨트롤 좌표를 실제로 조회해 **겹침 0 · 최하단 604 < 클라이언트 628**을 확인했다(08-07의 "설정 화면이
깨졌다" 재발 방지).

**검증**: 테스트 **55 green** · clippy 무경고 · exe 0.64MB · 유휴 RSS 1.30MB.

**판단**

- `pack.ps1`은 게이트 실패 시 **포장하지 않고 중단**한다 — 예산 초과분이 배포로 새어 나가지 않게(DR-8).
  DLL 검사는 `dumpbin`이 있을 때만 하므로, 릴리스 전에는 Developer PowerShell에서 돌리라고 문서에 못 박았다.

**실측**: `pack.ps1` 실행 — exe **0.64MB**(게이트 ≤3MB 통과), 포터블 ZIP **355KB**
(`NexaMemKeeper.exe` + README + 라이선스 2종 + `PORTABLE.txt`) 생성 확인.

## 30차 — 메뉴의 "검색 지우기"가 검색칸을 비우지 않던 문제 (사용자 QA)

**증상**: 풀다운 메뉴에서 검색 지우기를 하면 목록은 전체로 돌아오는데 **하단 검색칸의 글자는 그대로** 남았다.

**원인**: 메뉴가 `set_filter(hwnd, None)`을 불렀다. 이 함수는 검색칸이 생기기 **전에** 쓰던 것으로,
`ListState.filter`만 직접 지우고 에디트 컨트롤은 손대지 않는다. 그래서 **입력 상태가 두 곳으로 갈라져**
화면(목록)과 검색칸이 어긋났다. 검색칸이 유일한 입력 경로가 된 뒤로는 남아 있을 이유가 없는 코드였다.

**해결**: 메뉴도 지우기 단추·Esc와 **같은 `clear_search()`**를 부른다(검색칸 비우기 → `EN_CHANGE` →
필터·목록 갱신). 갈라짐의 원인이던 `set_filter`는 제거했다. 상태는 검색칸 하나에만 둔다(15 §4의 단일 원천 규칙).

**검증**: 워커에 검색어를 넣어 지우기 단추가 뜨는 것(`visible=True`)을 확인한 뒤 메뉴 명령(ID 254)을
보내니 단추가 다시 숨었다(`visible=False`) — 검색칸이 실제로 비워졌다는 뜻. 테스트 54 green ·
유휴 RSS 1.30MB.

**증상**: "입력 후 X 버튼이 생기지만 눌러도 동작 없음. 너무 네모난 버튼처럼 보여."

**원인 두 가지**
1. **클릭 불통** — 지우기 단추가 표준 `BUTTON`이었고, 검색 에디트 **위에 겹쳐** 놓였다. 형제 창끼리는
   z-순서가 곧 히트 테스트 순서라 클릭이 밑의 에디트로 흘러갔다(그림은 단추가 나중에 그려져 보였을 뿐).
2. **모양** — `BS_FLAT` 표준 단추라 회색 면과 테두리가 그대로 보였다. 검색칸 안쪽에 얹는 글리프로는 어울리지 않는다.

**해결** — 지우기 단추를 **직접 그리는 작은 창**(`NexaMemKeeperClear` 클래스)으로 바꿨다.
- 평소엔 배경 없이 **MDL2 `ChromeClose`(U+E8BB)** 글리프만, **호버·누름일 때만 둥근 회색 배경**
  (호버 `#E8E8E8`, 누름 `#D0D0D0`, 반지름 6). 참고 이미지의 브라우저 탭 닫기와 같은 느낌.
- 호버는 `TrackMouseEvent(TME_LEAVE)`로 잡고, 상태(호버·누름)는 전역 없이 창의 `GWLP_USERDATA` 비트에 둔다.
- 클릭은 `SetCapture` + 뗄 때 좌표가 안에 있을 때만 부모에 `WM_COMMAND(ID_SEARCH_CLEAR)`(표준 단추 동작).
- z-순서를 `HWND_TOP`으로 못 박고 에디트에 `WS_CLIPSIBLINGS`를 줘서 **덮어 지워지지도, 가려지지도** 않게 했다.

**검증**: 워커를 띄워 자식 창을 조회 → `NexaMemKeeperClear` 18×18, 입력 시 표시(`visible=True`),
합성 클릭(`WM_LBUTTONDOWN`/`UP`) 후 **검색칸이 비고 단추가 숨는 것**을 확인. 테스트 54 green ·
exe 0.64MB · 유휴 RSS 1.34MB.

## 28차 — 축소 버튼이 먹지 않던 문제 · 낡은 exe 재기동 함정 (사용자 QA)

**① 축소가 안 되던 이유** — "작업 관리자, Application Frame Host 같은 대상은 축소 버튼이 동작하지 않아."
27차에서 넣은 *자식이 하나뿐이면 펼쳐 두기*를 **행 구성 단계**(`build_grouped_rows`)에서 강제했다.
그래서 접기 클릭이 `expanded`에서 키를 빼도, 다음 그리기에서 `child_rows <= 1` 조건이 다시 열어 버렸다
(2초 갱신이면 눈에 보이지도 않게 즉시 복원). **펼침의 진실은 `expanded` 하나뿐**이어야 한다.
→ 행 구성은 `expanded`만 보고, 기본 펼침은 `auto_expand_groups()`로 **묶음이 처음 등장할 때 한 번만**
목록 창이 심는다(`seeded` 집합). 접으면 접힌 채로 남는다. 회귀 테스트로 고정.

**② 검색 중 펼침** — 접어 둔 묶음이라도 검색 중에는 펼쳐 그린다(일치한 자식이 접힘에 가려지면
`2026` 검색에서 창 행이 사라진다). 임시 집합으로 그리기만 하므로 **검색을 지우면 접힘이 그대로** 복원된다.

**③ 낡은 exe 재기동(오진)** — "목록 보기 버튼이 동작하지 않아."
코드 문제가 아니라 `target
elease\mk-app.exe`(DR-12 이름 변경 **전** 산출물)를 재기동한 탓이었다.
옛 워커가 `--worker list`를 모르고 즉시 종료(exit -1)해 창이 뜨지 않았다. 낡은 산출물을 지우고
`NexaMemKeeper.exe`로 재기동해 정상 확인. 재발 방지로 [18 §3-1](../18-build-and-test.md)에 경고 추가.

**검증**: 테스트 **54 green** · clippy 무경고 · 유휴 RSS 1.32MB.

## 27차 — 친숙한 이름 · 앱의 도우미 프로세스 · 창 제목 검색 (사용자 QA)

**① 이름 표시** — "sublime_text.exe 대신 작업관리자처럼 Sublime Text로 보여줄 수 있어?"
작업 관리자가 쓰는 값은 실행 파일 **버전 리소스의 `FileDescription`**이다. `QueryFullProcessImageNameW`로
경로를 얻고 `GetFileVersionInfoW`/`VerQueryValueW`로 읽는다. 2초마다 500개를 다시 읽으면 안 되므로
**PID별 1회 조회 후 캐시**(종료된 PID는 매 갱신 때 정리). 값이 없으면 파일명을 그대로 쓴다.

**② 앱 아래 도우미 프로세스** — "터미널이 작업 관리자에선 3개인데 우리는 1개야."
작업 관리자의 앱 항목은 *창*뿐 아니라 **그 앱이 띄운 자손 프로세스**까지 합쳐 `터미널(3)`으로 센다.
앱 묶음에 `owned_children`(자손 중 창이 없는 것)을 포함하고, 그 자손은 백그라운드 구획에서 제외해
**중복 노출을 막는다**. 메모리·쓰레드 합계도 자손을 포함한다.

**③ 셸은 예외** — "작업관리자는 espansod.exe를 개별로 보여주는데 우리는 explorer.exe 하위에 있어."
정보가 다른 게 아니라 **표시 규칙**이 달랐다. 시작프로그램·바탕화면에서 실행한 모든 것은 PPID상
`explorer.exe`의 자식이므로, 셸을 그대로 부모로 취급하면 무관한 프로그램이 탐색기 밑으로 들어간다.
→ `is_shell_host`(현재 `explorer.exe`)는 **자식을 거느리지 않는 것으로** 본다(작업 관리자와 동일).

**④ 창 제목 검색** — "`2026`을 넣으면 2줄이 보이면 좋겠어."
묶음 보기 검색을 `filter_grouped`로 분리했다. 이름·PID에 더해 **창 제목**까지 찾고, 제목만 걸린
경우 **일치한 창만** 남겨 `Slack.exe`(앱 행) + `2026-… - Slack`(창 행) 두 줄이 되게 한다. 또한 묶음
보기는 검색 중에도 평면으로 떨어지지 않고 구조를 유지한다(트리 보기의 조상 유지 규칙과 짝).

**검증**: 테스트 **54 green**(창 제목 검색·셸 예외 회귀 테스트 추가) · clippy 무경고 · Release 재기동
후 유휴 RSS **1.30MB**.

## 26차 — 작업 관리자와 같은 기준의 목록 구성 · 알림 자동 닫힘 (사용자 요청/QA)

**요청**: "윈도우 작업 관리자와 동일한 기준으로 프로세스 트리를 구성해줄 수 있어? 지금 보여지는 내용이 너무 다른 보기 형태라 혼돈이 있어."

**무엇이 달랐나**: 우리는 **원시 PPID 계층**을 그대로 보여줬다. 그래서 `msedge.exe` 하나 아래 자식 20개가 늘어서는 식이라, 작업 관리자의 *앱 / 백그라운드 프로세스 / Windows 프로세스* 3구획 + 프로그램별 묶음과 전혀 달라 보였다.

**작업 관리자와 같은 기준으로 재구성(DR-14)**:
- **분류**(`categorize`) — ① **앱**: 보이는 최상위 창을 가진 프로세스 ② **Windows 프로세스**: 세션 0(서비스·시스템)과 커널 의사 프로세스 ③ **백그라운드**: 나머지.
- **프로그램별 묶음** — 같은 실행 파일이 여럿이면 `Code.exe (25)`처럼 하나로 묶고 메모리를 합산한다. 펼치면 개별 프로세스가 보인다(작업 관리자의 `Microsoft Edge(24)`와 같은 형태).
- **앱 행에는 창 제목을 함께** 표시(`msedge.exe — New chat - Claude …`).
- 수집 추가: `SYSTEM_PROCESS_INFORMATION.SessionId` + `EnumWindows`로 **보이는 최상위 창**(소유 창·도구 창 제외, 제목 있는 것)의 PID→제목 맵.
- 보기 모드 3종으로 정리 — **앱별 묶음(기본)** / 프로세스 트리(PPID) / 평면 목록. 설정 `ui.view_mode = grouped|tree|flat`(구 `view_flat` 1회 마이그레이션).

**표시 다듬기(같은 QA에서 발견)**: 분류 머리글이 **선택된 것처럼 파랗게** 보였다 — 초기 선택값 `(0,0)`이 분류 행의 `pid=0`과 겹친 탓. 선택 없음 값을 `(u32::MAX, u32::MAX)`로 바꾸고, 분류 머리글은 **선택 대상에서 제외**하며 헤더 색으로 그린다. 분류·묶음 행에는 PID를 표시하지 않는다(작업 관리자와 동일).

**알림 자동 닫힘(사용자 QA)**: 풍선 알림이 닫기 전까지 우하단에 남아 있었다. Windows 10/11은 `NOTIFYICONDATA.uTimeout`을 무시하므로, **6초 뒤 빈 `szInfo`로 `NIM_MODIFY`를 보내 배너를 직접 내린다**(타이머 분리 — 폴링 타이머와 섞이지 않게 ID를 나눔).

**검증**: 캡처 확인 — `앱 (11)`에 창 제목, `백그라운드 프로세스 (315)`에 `Code.exe (25)`·`Slack.exe (6)` 묶음. 테스트 **51 green**.

## 25차 — 기본 보기 = 프로세스 트리 · 쓰레드는 보기 옵션 (사용자 요청)

**요청**: ① 하위 쓰레드는 큰 의미가 없으니 **작업 관리자처럼 프로세스 계층만** 기본으로 보이게 ② 쓰레드는 **보기 옵션**으로 켜고 끄되 기본은 끔 ③ **부모-자식 관계 보기를 기본**으로 하고 개별(평면) 보기도 옵션으로.

**구현**:
- `build_rows`·`build_rows_flat`에 `show_threads` 인자 추가 — 꺼져 있으면 쓰레드 행을 만들지 않고, **쓰레드만 있는 프로세스는 확장 버튼도 표시하지 않는다**(빈 확장으로 오해할 여지 제거).
- 보기 메뉴에 **쓰레드 표시(&H)** 체크 항목 추가(기본 off). 설정 `ui.show_threads = false`로 저장·복원.
- 기본 보기를 **프로세스 트리**로 되돌림(`ui.view_flat = false`). 평면 목록은 보기 메뉴 옵션으로 유지.
- **접힘 때문에 못 찾는 문제 재발 방지**(08-07 15차 사례): 트리로 열거나 전환할 때 **자식이 있는 프로세스를 자동으로 펼친다**. 검색 중에는 여전히 평면으로 보여주므로 계층에 숨지 않는다.

**검증**: 트리 기본 화면 캡처 — `msedge.exe` 부모 아래 자식들이 들여쓰기로 보이고 상태 줄이 `tree view`. 쓰레드 행은 없음. 테스트 **51 green**(쓰레드 기본 숨김 검증 추가).

## 24차 — 프로세스 종료 시 UI가 멈추던 문제 (사용자 QA)

**증상**: 목록에서 **프로세스 트리 종료**를 실행하면 창이 "응답 없음"이 된다. 사용자 관찰대로 **시간이 지나면 종료도 되고 UI도 복구**된다 — 교착이 아니라 **블로킹**이었다.

**원인**: 종료 로직을 **UI 스레드에서 동기 실행**했다. `run_kill`은 정상 종료를 최대 3초 기다리고(WM_CLOSE 후 `WaitForSingleObject`), 실패하면 강제 종료 후 다시 2초를 기다린다. 트리 종료는 이걸 **프로세스 수만큼 반복**하므로 메시지 루프가 그 시간 내내 막힌다.

**조치**: 회수·종료(트림/프로세스/트리/쓰레드)를 **백그라운드 스레드**로 옮기고 완료 시 `WM_ACTION_DONE`을 창에 게시한다. 진행 중에는 `BUSY` 플래그로 중복 실행을 막고 상태 줄에 "처리 중…"을 표시한다.

**검증**: 창 응답성을 `SendMessageTimeout(WM_NULL)`로 측정 — 8ms 응답, `IsHungAppWindow=false`. 테스트 50 green.

**되짚어보면** — M1에서 워커를 별도 프로세스로 뺀 이유(DR-7)가 "긴 작업이 셸을 막지 않게"였는데, 정작 **목록 창 안에서는 같은 실수를 반복**했다. 창 하나 안에서도 "기다리는 일은 UI 스레드 밖으로"가 같은 원칙이다.

## 22차 — 메뉴 토글 시 목록 창이 즉시 종료되던 버그 (사용자 QA)

**증상**: 메인 화면에서 **의사 프로세스 숨김을 해제**하면 UI가 멈추고 창이 사라진다. 트레이는 멀쩡하다.

**원인**: `RefCell` **이중 대여 패닉**. `sync_menu_checks`가 내부에서 `with_state_ret`으로 STATE를 다시 빌리는데, 호출부 4곳이 이미 `with_state(...)` **안**이었다.

```
with_state(|st| {                 // borrow_mut() 시작
    st.hide_pseudo = !st.hide_pseudo;
    sync_menu_checks(st.menu, …); // ← 내부에서 또 borrow_mut() → panic
});
```

릴리스 프로파일이 `panic = "abort"`(DR-4 성능 우선)이라 **스택 되감기 없이 프로세스가 즉시 죽는다**. 트레이가 멀쩡한 이유는 목록 창이 별도 워커 프로세스이기 때문 — **DR-7 하이브리드 격리가 의도대로 작동**해 셸까지 함께 죽지 않았다.

**영향 범위**: 의사 프로세스 숨김뿐 아니라 **보기 모드 전환·갱신 주기 변경·자동 실행 토글**도 같은 경로라 전부 같은 증상이었다(사용자가 그중 하나를 먼저 만난 것).

**조치**: `sync_menu_checks`가 STATE를 만지지 않도록 **필요한 값(flat)을 인자로 받게** 변경하고 호출부 5곳을 갱신. 함수에 "여기서 STATE를 다시 빌리면 안 된다"는 이유를 주석으로 남겼다.

**검증**: 이전에 죽던 메뉴 명령 9개(의사 프로세스 ×2 · 트리/평면 전환 · 1/2/5초 · 자동 실행 ×2)를 연속 실행 → **창 생존 확인**. 테스트 49 green.

**교훈**: 상태를 `thread_local! RefCell`로 들고 있으면, 헬퍼가 상태를 "알아서 읽는" 편의가 곧 이중 대여 함정이 된다. **UI 헬퍼는 상태를 인자로 받는다**를 규칙으로 삼는다([15 §4](../15-dev-methodology.md)에 추가).

## 19차 — 설정 창 라벨 줄바꿈 수정 (사용자 QA)

**증상**: "최소 간격 (ms, 60000~1800000)" 라벨이 2줄로 접혀 아래가 잘렸다(18차에서 단위를 ms로 바꾸며 문구가 길어진 여파).

**원인**: 라벨 폭이 170px 고정인데 문구는 173px 필요. STATIC 컨트롤은 기본이 자동 줄바꿈이라 넘치면 다음 줄로 접히고, 컨트롤 높이는 18px 고정이라 두 번째 줄이 잘려 보였다.

**조치**: 라벨/입력 칸 규격을 상수로 통일 — `LBL_W=218` · `NUM_X=232` · `NUM_W=96`. 자동 정리·일반 그룹의 모든 행이 같은 열에 정렬되고, 입력 칸도 7자리(1800000)를 여유 있게 담는다.

**검증 방법(교훈)**: 컨트롤 높이만 재면 줄바꿈 여부를 알 수 없다(높이는 내가 준 18px 그대로). `WM_GETFONT`로 실제 폰트를 얻어 `GetTextExtentPoint32W`로 **필요 폭**을 재고 컨트롤 폭과 비교해야 확실하다. 실측 결과:

| 라벨 | 필요 | 컨트롤 |
| --- | --- | --- |
| 최소 간격 (ms, 60000~1800000) | 173px | 218px ✅ |
| 관찰 주기 (ms, 2000~30000) | 155px | 218px ✅ |
| 목록 갱신 (ms, 500~10000) | 149px | 218px ✅ |
| 주기 정리 (ms, 0=끔) | 116px | 218px ✅ |
| 임계값 (%, 50~95) | 101px | 218px ✅ |

**부수 관찰**: 검증 중 창을 못 찾아 헤맸는데, ① PowerShell에서 `$script:` 스코프로 콜백 결과를 받아야 하고 ② 내가 띄운 설정 창을 사용자가 닫으면 당연히 사라진다는 두 가지가 겹친 것이었다. 코드 문제 아님.

## 18차 — 설정 시간 단위 ms 통일 (사용자 요청)

**무엇**: 설정 화면의 시간 값이 초·분·ms로 섞여 있던 것을 **전부 밀리초로 통일**.

| 항목 | 이전 | 이후 |
| --- | --- | --- |
| 관찰 주기 | `poll_secs` 5초 (2~30) | `poll_ms` **5000** (2000~30000) |
| 정리 최소 간격 | `cooldown_secs` 300초 (60~1800) | `cooldown_ms` **300000** (60000~1800000) |
| 주기 정리 | `interval_mins` 0분 (10~240) | `interval_ms` **0** (600000~14400000) |
| 목록 갱신 | `list_refresh_ms` 2000 | 그대로 |

**마이그레이션**(docs/09 §7-4 "키 개명 금지 — 신규 키 + 1회 마이그레이션"): 구 키를 읽으면 ×1000·×60000으로 환산해 새 필드에 넣고, 저장 시 새 키로만 쓴다. 구 키는 "모르는 키 보존" 대상에서 제외해 파일에 남지 않는다.

**실기 검증**: 구 버전 파일(`poll_secs=8`·`cooldown_secs=420`·`interval_mins=20`)을 두고 실행 → 설정 창에 8000·420000·1200000으로 표시 → 저장 후 파일이 `poll_ms = 8000`·`cooldown_ms = 420000`·`interval_ms = 1200000`으로 재작성됨을 확인. `should_auto_clean`도 ms 기준으로 바꾸고 테스트 갱신(**38 green**).

**부수 정리**: `interval_ms`는 0(끔)이거나 600000ms(10분) 이상만 허용 — 이전 분 단위 범위(10~240분)를 ms로 옮긴 것. 설정 창 라벨도 전부 `(ms, 범위)` 표기로 바꿨다.

## 15차 — "프로그램을 목록에서 찾을 수 없다" 원인·해결 + 앱 아이콘 (사용자 문의/요청)

**문의**: "Nexa Markdown Viewer가 떠 있는데 목록에서 찾을 수 없다."

**원인(실측)**: 버그가 아니라 **트리 기본 보기의 구조적 함정**이었다. `NexaMarkdownViewer.exe`(PID 35624)의 부모가 `explorer.exe`(PID 3200)라서 **explorer 노드가 접힌 상태에서는 자식이 화면에 없다**. 전체 491개 중 고아(부모가 이미 종료)는 82개뿐이라, **나머지 400여 개가 부모 아래 숨어 있었다** — 탐색기·셸에서 띄운 앱은 전부 여기 해당한다. M3에서 평면 목록을 트리로 바꾸면서 발생한 회귀.

**해결 3종**:
1. **기본 보기 = 평면 목록**(`build_rows_flat`) — 계층 없이 전부 나열(작업 관리자 "자세히"와 동일). 트리는 **보기 메뉴**에서 선택.
2. **보기(&V) 메뉴 신설** — 평면 목록 / 프로세스 트리(체크 표시) · 모두 펼치기 / 모두 접기 · 검색 지우기. "모두 펼치기"는 **자식 있는 프로세스만** 펼친다(전부 펼치면 쓰레드가 수천 줄이 된다).

## 13차 — 권한 실측 답변 · 의사 프로세스 숨김 옵션 (사용자 문의/요청)

**질문 1: "관리자 권한으로 실행되어야 하나? 자동 시작되면서 설정이 가능한가?"** → 같은 PC에서 승격/비승격을 연속 실행해 실측하고 [07 §4](../07-adr-0002-memory-reclaim.md)에 표로 기록.

| | 일반 권한(제한 토큰) | 관리자 승격 |
| --- | --- | --- |
| 워킹셋 트림 | 115개 성공 / 378 제외 | **466개** / 25 제외 |
| 영역② 스탠바이 퍼지 | `0xC0000061`(PRIVILEGE_NOT_HELD) 실패 → partial | NTSTATUS 0 성공 |
| 회수량 | **+322MB** | **+847MB**(2.6배) |

→ **관리자 권한은 필수가 아니다.** 일반 권한으로도 관찰·목록·자기 세션 트림이 동작하고 실제로 회수된다. 승격은 "더 많이" 회수하기 위한 선택지이며, 생략된 영역은 알림에 명시된다.
자동 시작과 권한 관계도 [07 §4-1](../07-adr-0002-memory-reclaim.md)에 정리: 현재 구현(`HKCU\…\Run`, DR-11)은 **일반 권한 시작**이고 Windows 정책상 Run 키로는 승격이 불가능하다. 승격 자동 시작이 필요하면 **작업 스케줄러 "가장 높은 수준의 권한으로 실행"**이 표준 해법(FR-6에 계획, 미구현).

**요청 2: "의사 프로세스도 숨기는 옵션을, 기본은 숨김으로"** → 구현.
- mk-core `is_pseudo`/`filter_pseudo` + 테스트(숨김 대상 = Memory Compression·MemCompression·Registry·Secure System / **System·System Idle Process는 제외** — 작업 관리자도 이 둘은 표시한다). 테스트 **23 green**.

**교훈(재기동 절차 정정)**: 실행 중인 exe를 Windows가 잠그므로 `cargo build --release`를 먼저 하면 `os error 5`로 링크 실패한다. 더 위험한 건 **빌드 실패를 놓치고 옛 바이너리를 재실행**하는 것(이번에 실제로 한 번 발생 — 재기동은 됐으나 새 기능이 없는 바이너리였다). → [18 §3-1](../18-build-and-test.md) 절차를 **중지 → 빌드 → 실행** 순서로 정정.

**교훈 2건**:
1. **PowerShell로 GUI 서브시스템 exe의 종료 코드를 못 잰다** — `& $exe`가 대기하지 않아 항상 0. 릴리스 빌드 검증은 디버그 빌드(콘솔 있음)로 하거나 `Start-Process -Wait` 필요. 셸의 `Command::status()`는 서브시스템과 무관하게 정상 대기.
2. **영역②(스탠바이 퍼지)는 `Available` 수치를 올리지 않는다** — Standby도 Free도 모두 Available에 포함되므로(docs/19 §2-1) 퍼지는 Available 내부 이동일 뿐. 보고된 +209MB는 **영역①(트림)의 성과**다. 회수량 수식(docs/19 §4-3 = Avail 델타)은 트림 효과를 정직하게 반영하므로 유지 — 숫자 부풀리기가 없다는 점에서 오히려 적합.

## 3차 — 판단 우선순위 확정(DR-4) → ADR-0003 권고 정정 (사용자 확정)

**무엇**: 사용자 지시 "개발·배포의 편의성보다 성능·동작 안정성이 더 중요" → **DR-4로 고정**([10 §1](../10-decision-record.md)), [00 비전](../00-vision.md) 설계 원칙 0으로 반영.

**정정된 판정**:
- [ADR-0003](../08-adr-0003-resident-architecture.md): 단일 프로세스 권고 → **하이브리드 권고로 정정**. 최초 A 우위 근거가 "IPC 복잡도"(= 개발 편의)였는데 DR-4 기준상 무효 — B의 100% 회수 보장·크래시 격리(안정성)가 우선. 성능 열세(워커 spawn ~50-150ms)는 즉시성이 필요한 Top 5 팝업만 셸에 남겨 소거. 원래 판정문은 취소선 보존(규칙 5).
- [ADR-0001](../06-adr-0001-stack.md): 권고 A(Rust) 유지·논거 강화 — C/C++ 대비 우위 축을 개발 편의가 아닌 **안정성**(수동 메모리 관리의 크래시 면적 vs 컴파일 타임 안전)으로 재정리. C#/Go 탈락 사유에 GC 정지·점유 변동(안정성) 추가.

**부수 이득 기록**: 하이브리드 구조에서 승격 필요 정리 영역(②~⑥)은 워커만 승격 가능 — 상주 셸은 항상 일반 권한 유지(08 §4-5).
